## Evidence and test boundaries

**Source-confirmed** means the implementation supports the described trigger and outcome, but that scenario was not executed in the browser. **Browser-observed** means the root auditor reproduced the visible behavior in the local application. Combined findings identify both kinds of evidence. Source paths below are relative to the audited checkout; line numbers refer to that snapshot.

The browser ran the real UI against an existing `FakvioFactory` InMemory fixture, using synthetic accounts `ux0@example.test`, `ux1@example.test`, and `ux2@example.test`, two companies, and an email stub. Fixture tenant data is shared: these tests do **not** establish tenant isolation. No production system or real SMTP/OAuth/2FA provider was exercised. CAPTCHA flow was not tested.

Browser coverage included User login with company A, confirmation and reload when switching A → B with Accountant role, SysAdmin login and Users navigation, desktop around 1270 px, and mobile at 390 px and 320 px. Settled mobile layouts fit those widths; transitional resize screenshots are not evidence of overflow. This was targeted verification, not a complete application end-to-end pass.

## Findings

### 1. P1 — Secondary-company membership cannot be individually revoked

**Source-confirmed; high confidence.** Grant an existing account access to a second company, then attempt to remove only that access or change that membership's role. The membership API/service expose invitation and acceptance without an individual revoke/update operation, while Users edits the legacy primary-company relationship. Re-inviting an active member is rejected. Administrators cannot complete a normal access-removal lifecycle without broader account action.

Add a membership list with company, effective role, status, and explicit per-membership role/revoke actions, supported by authorized API operations. Preserve access to unrelated companies.

Sources: `Fakvio.API/Controller/MyCompaniesController.cs:17–54`; `Fakvio.Application/Service/ICompanyMembershipService.cs:7–11`; `Fakvio.UI.Shared/Components/Pages/Users.razor:37,44,238–242,278–280`; `Fakvio.Infrastructure/Service/UserService.cs:302–317`; `Fakvio.Infrastructure/Service/CompanyMembershipService.cs:132`.

### 2. P1 — Saving client edits silently removes additional contacts

**Source-confirmed; high confidence.** Open a client with several contacts, change its company name, and save. The editor loads only the first email and phone and sends those as the replacement collection. Additional contacts, labels, and existing primary flags are lost even when contacts were not the intended edit.

Preserve unedited contacts and metadata, or provide a reusable full contact-list editor. Sources: `Fakvio.UI.Shared/Components/Pages/ClientDetail.razor:588–591,677–695`; `Fakvio.Infrastructure/Service/ClientService.cs:540–553`.

### 3. P2 — Invalid OAuth consent tickets bypass the intended recovery state

**Source-confirmed; high confidence.** Open consent with an expired/invalid ticket that produces HTTP 400. The Describe request throws before `_loading` is cleared; the subsequent null-result branch cannot handle this response. The user receives an error-boundary/loading failure instead of the intended invalid-ticket explanation and restart path.

Catch the typed API error, clear loading in `finally`, and present a localized reconnect action. Sources: `Fakvio.UI.Shared/Components/Pages/OAuthConsent.razor:146–152`; `Fakvio.UI.Shared/Services/ApiClientBase.cs:215`. No real OAuth provider flow was tested.

### 4. P2 — Registration permanently says to check email after delivery failed

**Source-confirmed; high confidence.** Registration returns a successful account creation with `EmailSent=false`. `_isSuccess` is still set; a temporary warning reports failure, but the persistent success view tells the user to check email. After the warning disappears, there is no accurate explanation of the remaining step.

Persist the delivery outcome and provide an appropriate retry/recovery action. Source: `Fakvio.UI.Shared/Components/Pages/Register.razor:35–40,198–212`. Real SMTP was not tested.

### 5. P2 — Two-factor service outages are reported as an invalid code

**Source-confirmed; high confidence.** Submit a valid code while the verification request fails. The API service converts failures to null, and the page interprets null as an invalid code, prompting pointless retries and obscuring the service problem.

Distinguish invalid credentials from transport/server failure and retain a retryable error state. Sources: `Fakvio.UI.Shared/Services/TwoFactorApiService.cs:83–92`; `Fakvio.UI.Shared/Components/Pages/TwoFactorVerification.razor:126`. Real two-factor verification was not executed.

### 6. P2 — A second API-key creation replaces the first one-time secret

**Source-confirmed; high confidence.** Create a key, leave its one-time reveal open without copying it, then create another key. The create action remains available and `_createdKey` is overwritten. The first key remains created, but its secret is no longer retrievable from this view.

Require an explicit acknowledgement/dismissal before another creation, or clearly warn that the first secret will be lost. Source: `Fakvio.UI.Shared/Components/Pages/Integrations.razor:75,367`. The destructive sequence was not browser-tested.

### 7. P2 — Invitation submission silently does nothing when company is missing

**Browser-observed and source-confirmed; high confidence.** In the SysAdmin invitation dialog, enter a valid email, leave company unselected, and submit. There is no action or field error. The selector lacks required validation and the handler silently returns for the missing company.

Use a validated required company field and focus its error on submit. Source: `Fakvio.UI.Shared/Components/Shared/InviteCompanyMemberDialog.razor:19–21,50`. [Screenshot](ux-2026-10-01/invitation-no-validation.png).

### 8. P2 — Credit-note creation has incomplete original-invoice selection

**Source-confirmed; high confidence.** Open ordinary invoice creation and change document type to Credit Note: the required original-invoice selector remains empty because candidates load only during initial credit-note initialization. Even when entering directly as a credit note, only the first 200 completed and first 200 paid invoices are fetched, so older eligible invoices can be inaccessible.

Reload dependent data when document type changes and use a searchable, server-paged selector that also resolves any preselected original ID. Source: `Fakvio.UI.Shared/Components/Pages/InvoiceDetail.razor:75–90,992–995,1051–1065`. The browser inspected this form, but did not establish these backend-dependent failure cases.

### 9. P2 — Invoice/client creation allows repeated submissions during a slow save

**Source-confirmed; high confidence for duplicate requests.** Double-click Create while the first POST is outstanding. The buttons have no submitting state and handlers have no re-entry guard. Multiple requests can create duplicate records where server constraints do not reject them; actual duplicate persistence was not tested.

Guard the handler, disable submit while saving, and show progress. Sources: `Fakvio.UI.Shared/Components/Pages/InvoiceDetail.razor:50,1518–1547`; `Fakvio.UI.Shared/Components/Pages/ClientDetail.razor:48,612–624`.

### 10. P2 — Payment pagination cannot reach the complete history

**Source-confirmed; high confidence.** With more than 50 matching transactions, use the history pager. The page always fetches server page 1 with 50 items, then applies a local table pager to that subset; the displayed total can be larger than the accessible history. Unmatched incoming payments similarly stop at 100 without paging.

Bind server paging to the selected page/page size and server total, including the unmatched list. Source: `Fakvio.UI.Shared/Components/Pages/Payments.razor:194,282–289,336–337,379–380`.

### 11. P2 — Some visible grid filters are ignored

**Source-confirmed; high confidence.** Filter the invoice total-amount column or the status column in client invoice history. Global column filtering exposes the controls, but loaders do not translate the amount filter; client history takes status only from its separate toolbar selector. Results therefore do not match the apparent filter state.

Implement the corresponding server filters or disable unsupported controls; consolidate status filtering. Sources: `Fakvio.UI.Shared/Components/Shared/FakvioGrid.razor:54–56`; `Pages/Invoices.razor:143,595–615`; `Pages/ClientDetail.razor:388,883` (both under `Fakvio.UI.Shared/Components`).

### 12. P2 — Client history ends without an invoice-detail action

**Source-confirmed; high confidence.** Find an invoice inside a client's history and try to inspect it. The grid has no row-click action, detail link, or action column; document numbers are plain chips. Users must leave and search again in the invoice list.

Render document numbers as real links to invoice details, supporting mouse and keyboard navigation. Source: `Fakvio.UI.Shared/Components/Pages/ClientDetail.razor:354–395`.

### 13. P2 — Ordinary Users see settings write actions they cannot complete

**Source-confirmed; high confidence.** Sign in as User, open VAT rates, numbering, or content templates, fill a create/edit form, then save. The UI exposes write actions while the API requires Admin/SysAdmin, so the workflow ends in 403 after the user has invested effort.

Apply the same capability checks to UI actions; keep permitted read views. **Accountant is allowed:** its internal role is Admin, so this finding applies only to ordinary User. Browser checks verified the role labels, not every denied write.

Sources: `Fakvio.UI.Shared/Components/Layout/NavMenu.razor:54–55`; `Pages/VatRates.razor:22,75,103`; `Pages/NumberSequences.razor:25,91`; `Pages/ContentTemplates.razor:20,87` (pages under `Fakvio.UI.Shared/Components`); API controllers `VatRateController.cs:155,187`, `NumberSequenceController.cs:88,272`, `ContentTemplateController.cs:116,142` under `Fakvio.API/Controller`. Role mapping: `Fakvio.UI.Shared/Services/CustomAuthenticationStateProvider.cs:270`; `Resources/SharedResource.en.resx:383`.

### 14. P2 — Notification failures appear as empty results or successful dismissal

**Source-confirmed; high confidence.** When notification reads fail, the service returns an empty list or zero count. Failed mark-read requests are swallowed, and the bell still updates its local items/count as though the change succeeded. Users can falsely conclude there is nothing needing attention; dismissed items can later reappear.

Retain the last successful state, return explicit failure results, show a localized retryable error, and update read status only after success. Sources: `Fakvio.UI.Shared/Services/NotificationApiService.cs:45–47,61–63,93–95,109–111`; `Components/Notification/NotificationBell.razor:157–168`; `Components/Pages/Notifications.razor:25` (all under `Fakvio.UI.Shared`).

### 15. P2 — Unsaved feedback replies can be lost on navigation

**Source-confirmed; high confidence.** Type an unsent reply in feedback detail, then navigate away. The reply field has no dirty-state navigation protection, unlike protected invoice/client forms. Users can lose a drafted response without warning.

Track the draft and use the existing unsaved-change guard or persist the draft. Source: `Fakvio.UI.Shared/Components/Shared/FeedbackDetail.razor:29–31`.

### 16. P2 — Feedback triage omits reporter and company context

**Source-confirmed; high confidence.** Open the SysAdmin feedback inbox/detail for reports from several companies. The shared list and detail omit reporter/company identity, making it difficult to establish which tenant and person need assistance from the report itself.

Show available reporter and company context in the administrator view, with clear fallbacks for unavailable identity. Sources: `Fakvio.UI.Shared/Components/Shared/FeedbackList.razor:17–27`; `FeedbackDetail.razor:14–24` in the same directory.

### 17. P2 — Pasting a full URL into feedback produces an unhelpful generic error

**Browser-observed and source-confirmed; high confidence.** Enter a valid title/description and paste `http://localhost:5145/users` into the editable Page field, then submit. The browser showed a generic failure message without identifying the field. The field provides no path-format instruction; submission normalizes a relative path and rejects the full URL.

Explain the accepted format and show a field-level validation error; optionally normalize supported same-origin URLs safely. Source: `Fakvio.UI.Shared/Components/Shared/FeedbackDialog.razor:17,57–58`. [Screenshot](ux-2026-10-01/feedback-url-error.png).

### 18. P2 — Setup guidance exposes technical names and routes users to restricted settings

**Browser-observed raw field names; source-confirmed route mismatch; high confidence.** An incomplete tenant sees identifiers such as `IsIssuer`, `EpoTaxOfficeCode`, and `EpoTaxOfficeBranchCode`. The EPO fix route targets `/company-settings`, which is SysAdmin-only, so ordinary tenant users cannot use the advertised correction path. The route was not clicked in the browser.

Map missing-field identifiers to localized form labels and direct the fix action to a permitted tenant settings flow, or explain that administrator intervention is required. Sources: `Fakvio.UI.Shared/Components/Shared/SetupChecklist.razor:85`; `Fakvio.Infrastructure/Service/TenantReadinessService.cs:35,87,234–235`; `Fakvio.UI.Shared/Components/Pages/CompanySettings.razor:18`. ### 20. P3 — Language and accessible-name gaps remain in shared surfaces

**Browser-observed English grid strings and unnamed bell; source-confirmed hard-coded notification wording.** Czech Integrations shows “Filter value” and “0-0 of 0”; accessibility output exposes “Column options” and “Clear filter.” The notification bell is an unnamed button, and the notifications page hard-codes Czech controls instead of using the shared localization resources.

Configure grid localization and give the bell a localized accessible name; move notification labels to resources. Sources: `Fakvio.UI.Shared/Components/Notification/NotificationBell.razor:10–12`; `Components/Pages/Notifications.razor:10–28`; shared grid configuration `Components/Shared/FakvioGrid.razor:54–75` (under `Fakvio.UI.Shared`). Full keyboard and screen-reader journeys remain untested.

## Additional observations and exclusions

- Client deletion executes immediately without confirmation or undo (`Fakvio.UI.Shared/Components/Pages/Clients.razor:144`; `ClientDetail.razor:766` in the same directory). It is a soft delete; add a consistent confirmation or undo pattern rather than describing it as permanent data destruction.
- Invoice loading errors use a hard-coded English snackbar and then the normal empty state (`Fakvio.UI.Shared/Components/Pages/Invoices.razor:625–626`). Keep error and genuinely empty results distinct.
- Mobile company names hide while the switch menu remains usable. A persistent short current-company label would reduce context mistakes; this is a usability risk, not a demonstrated functional failure. [Mobile dashboard](ux-2026-10-01/mobile-dashboard.png).
- Currency `1` appeared in the fixture, but initialization falls back to ID 1 only when the currency list is empty (`InvoiceDetail.razor:1146`). Normal loaded items supply names. Excluded as a conclusive production finding.
- Both notification route maps send `BankTransaction` to `/payment-matching` rather than current `/payments`. A live notification producer for that entity was not established, so this remains a conditional follow-up rather than a ranked finding.
